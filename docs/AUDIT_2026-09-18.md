# A. Executive Summary

## Kondisi umum

Siap Tempur adalah codebase yang **jauh lebih sehat daripada rata-rata proyek seukurannya pada sumbu keamanan dan disiplin tipe**, tetapi sedang menanggung **beban teknis besar pada sumbu konsolidasi**: dua generasi arsitektur admin hidup berdampingan, definisi skema tersebar di tiga lokasi yang saling bertentangan, dan satu subsystem legacy berukuran ~10.800 baris yang sudah tidak dapat dijangkau tapi masih dipertahankan.

Verifikasi otomatis yang saya jalankan sendiri, hijau:

## Yang benar-benar bagus (jangan disentuh)

Ini penting dicatat supaya laporan tidak over-state masalahnya:

1. **Exam engine server-authoritative.** 0 dari 84 `page.tsx` adalah Client Component. 0 query tabel dari client. 0 RPC dari client. Nilai `score`, `duration`, dan `remaining time` **tidak pernah** dikirim dari browser. `finishPractice(sessionId)` hanya mengirim satu UUID.
2. **Timer ditegakkan di server**, `src/services/attempt-answer.service.ts:20-46` (+30 detik toleransi jaringan yang didokumentasikan).
3. **Kepemilikan attempt diperiksa di server** sebelum setiap penulisan jawaban: `attemptAnswerService.saveAnswer` memverifikasi attempt milik user, soal milik attempt, opsi milik soal (`:55-69`). Tidak ada IDOR di jalur ini.
4. **RLS + GRANT untuk kunci jawaban sudah tertutup pada peran `anon`** — saya verifikasi langsung ke staging: `attempt_questions`, `attempt_answers`, `question_versions`, `questions`, `profiles`, `audit_logs`, `leaderboard_entries`, `event_rankings` semuanya `401 permission denied` untuk `anon`.
5. **Tidak ada `as any`, tidak ada `@ts-ignore`, `strict: true`.** Disiplin tipe di batas modul sangat baik.
6. **CSRF konsisten** di action file V2 (`app/actions/practice.ts` 6/6, `app/actions/admin-v2.ts`, `app/actions/profile.ts`).
7. **Webhook Midtrans benar**: SHA-512 signature, `crypto.timingSafeEqual`, cek panjang heksadesimal dulu, tolak mismatch amount, idempoten via `(provider, event_id)` unik + `SELECT … FOR UPDATE`.
8. **Token debit idempoten dan aman secara DB**: `debit_exam_token_once` memakai `SELECT … FOR UPDATE`, unique index parsial `wallet_transactions_attempt_debit_idx`, dan **sudah di-revoke dari `anon`/`authenticated`** (`20260820124000:113-116`).
9. **Semua 98 tabel Schema V2 ber-RLS**; setiap policy UPDATE punya `WITH CHECK`; 64/64 fungsi `SECURITY DEFINER` bootstrap ter-pin `search_path`.
10. **Tidak ada secret bocor** — `.env.local` di-gitignore dan tidak terlacak git.

## Penilaian kesiapan

**Layak production: BELUM** — konsisten dengan keputusan dark launch yang sudah diambil.

Bukan karena ada eksploit yang terbukti berhasil (saya tidak menemukan satu pun P0 baru), tetapi karena **keadaan DB yang ter-deploy tidak dapat diverifikasi dari repo**, dan itu adalah properti yang harus dimiliki sebelum domain publik dibuka. Ditambah tiga temuan non-keamanan (skema di luar repo, audit log mati, scoring ganda) yang masing-masing akan menghasilkan insiden produksi jika dibiarkan.

# C. Top Critical Findings

Hanya yang terpenting, dalam urutan prioritas.

### C1 — Skema Schema V2 tidak dapat direkonstruksi dari repo
**P0 · CONFIRMED.** `exam_attempts`, `attempt_answers`, `attempt_questions`, `attempt_scores`, `wallets`, `wallet_transactions`, `entitlements`, `products`, `programs`, `tracks`, `exams`, `question_options`, `question_versions`, `order_items` — **0 file migration** yang memuat `CREATE TABLE` untuk tabel-tabel ini. `supabase/schema.sql` mendeskripsikan skema V1 (8 tabel, enum `question_type as enum ('TWK','TIU','TKP')`). DDL nyata ada di `scripts/cutover/bootstrap/*.sql` (22 file). README migrasi sendiri mengakui: *"Ini deklarasi baseline, bukan klaim bahwa setiap file dijalankan satu per satu."* **Dampak:** tidak ada staging/CI/preview environment yang bisa dibangun ulang; drift pasca-baseline tidak terdeteksi; 25 fungsi SQL termasuk seluruh RPC ujian TKA tidak terlihat oleh `db push`.

### C2 — `app/actions/admin.ts` adalah kode mati yang terbukti mati
**P1 · CONFIRMED (kode + DB).** 1.302 baris, 37 action. 8 pengimpornya semua tidak terjangkau, dan 12 tabel yang ditulisnya tidak ada di DB. **Dampak:** ini menyelesaikan ambiguitas "dua model authorization" — hanya satu yang hidup. Menghapusnya adalah pembersihan, bukan refactor.

### C3 — Audit log 100% gagal, senyap
**P1 · CONFIRMED (kode + DB).** `lib/audit-log.ts:22-29` menulis `actor_id, target_type, target_id, details`; DB punya `actor_user_id, entity_type, entity_id, old_data, new_data, user_agent`. Error ditelan `logger.warn`. 12 pemanggilan = 12 kegagalan. **Dampak:** seluruh klaim audit trail admin tidak benar. `audit_logs` juga deny-all (0 policy terbaca untuk `anon`/`authenticated`) sehingga tidak ada jalur review audit.

### C4 — Dua engine scoring, skala tidak kompatibel
**P0/P1 · CONFIRMED.** `src/domain/question-response.ts` memberi `single_choice` hingga 5 poin; `app_private.score_exam_attempt` (bootstrap `10_functions_app_private_s_z.sql:326-424`) memberi 1 poin, `category` → pecahan 0..1, dan menulis `passing_score, passed = NULL`. **Dampak:** `total_score` TKA dan CPNS tidak sebanding; peringkat lintas-jalur tidak bermakna; status kelulusan TKA permanen kosong.

### C5 — Write-on-GET dengan service role di halaman publik
**P2 · CONFIRMED.** `app/cpns/page.tsx:44-45` → `lib/tryout-event-status.ts:10-15` melakukan `UPDATE tryout_events` saat render GET anonim. Tabelnya tidak ada, jadi selalu gagal. **Dampak:** GET tidak idempoten, kredensial admin di jalur anonim, halaman SEO tidak dapat di-cache, section event landing selalu kosong.

### C6 — `fraud_status` Midtrans tidak divalidasi
**P1 · CONFIRMED (omisi), POSSIBLE (dampak).** Satu-satunya kemunculan di repo adalah deklarasi tipe `lib/midtrans.ts:53`. Pemenuhan order hanya melihat `transaction_status`. **Dampak:** potensi pemenuhan gratis pada `capture` + `deny`, tanpa claw-back karena guard status monotonik.

### C7 — Bug yang terlihat pengguna: key React dari field yang dapat diedit
**P1 · CONFIRMED.** `components/admin/QuestionOptionsEditor.tsx:106,110` — `key={`${row.key}-${index}`}` sementara `row.key` di-bind ke `<input>`. Setiap ketikan mengubah key → baris di-unmount → fokus hilang. **Dampak:** admin hanya bisa mengetik satu karakter per klik. Reachable di `/admin/content/review` yang **hidup**.

### C8 — `auth.getUser()` 2–3× per render
**P2 · CONFIRMED.** 47 file memanggil `auth.getUser()`. `/cpns/dashboard/tryout/[sessionId]` memanggil **3×** (2 layout + 1 page). `getUser()` @supabase/ssr memvalidasi JWT ke server Auth, tidak di-dedupe React/Next. Semua rute `force-dynamic`. **Dampak:** biaya latensi di jalur start-ujian, tepat di alur yang paling perlu stabil.

**Attempt yang sama, dua kunci jawaban berbeda.** Jika admin memperbaiki kunci soal setelah peserta mengerjakan, jalur CPNS menilai ulang dengan kunci **baru** (termasuk saat resume/skor ulang attempt lama), sementara jalur TKA tetap memakai kunci **lama**. Ini juga membuat hasil tidak dapat direproduksi dan melemahkan klaim audit. Ini **temuan baru** dan memperkuat C4: bukan hanya skala yang berbeda, tetapi sumber kebenaran yang berbeda.

**Recommended Architecture**
Selalu menyekor dari `question_snapshot` (beku), di kedua jalur. Snapshot yang membeku adalah properti yang benar dan sudah dipilih jalur TKA.

**Risk of Change:** Medium — mengubah perilaku penilaian ulang; perlu keputusan apakah attempt lama perlu diskor ulang.

### [P1] `recalculate_event_rankings` tanpa index yang dapat dipakai, dipanggil di banyak jalur panas
**Category:** Database / Performance · **Confidence:** CONFIRMED · **Risk of change:** Low

**Files**
* `supabase/migrations/20260820131000_schema_v2_event_ranking_recalculation.sql:20-22` (predikat), `:60-66` (UPDATE semua peserta)
* Pola sama di `app/actions/event-leaderboard.ts:75-81`

**Problem**
Predikatnya `lower(a.status) = 'completed' AND a.metadata->>'eventId' = p_event_id::text`. Tidak ada GIN pada `metadata`, tidak ada expression index, dan pembungkus `lower()` **mematikan** index `exam_attempts(exam_id, status)` yang ada. Lalu `:60-66` melakukan `UPDATE exam_attempts SET rank, updated_at = now()` untuk setiap peserta.

**Impact**
Dipanggil pada **setiap** submit attempt event, setiap tampilan leaderboard event yang selesai, dan setiap klaim sertifikat. Biayanya scan penuh + update massal, bertambah dengan jumlah peserta.

**Recommended Architecture**
Expression index `ON exam_attempts ((metadata->>'eventId')) WHERE lower(status) = 'completed'`, atau kolom `event_id` yang terindex (lebih baik, karena `metadata->>` sebagai kunci pencarian panas adalah bau desain). Keluarkan rekalkulasi dari jalur submit (lihat G6).

**Risk of Change:** Low (migration aditif), Medium jika memilih kolom baru.

## G0b — Replay migrasi: apa yang saya verifikasi, dan satu koreksi

Claim "urutan migrasi menyebabkan penghapusan data" saya **verifikasi ulang sendiri**, karena klaim seperti itu tidak boleh masuk laporan tanpa bukti. Hasilnya **sebagian berbeda** dari yang dilaporkan audit DB, dan koreksinya penting.

**Yang saya reproduksi (dan bertahan):**

```text
Seed 20240223*_seed_*.sql memakai DO $$ ... $$ dengan INSERT polos.
Hasil grep "on conflict | if not exists | where not exists":
  202402230002_seed_tiu_analitis.sql : 0
  202402230003_seed_tiu_analogi.sql  : 0
  202402230004 ... 0006              : 0
→ SEED TIDAK IDEMPOTEN. Dijalankan dua kali = soal duplikat.
```

Jadi risiko replay yang nyata adalah **duplikasi data**, bukan penghapusan. Ini dikonfirmasi: 12 dari 161 migration memuat statement non-idempoten yang keras (semuanya pra-baseline → laten hari ini, tetapi `db reset` akan gagal pada 3 di antaranya).

**Yang TIDAK bertahan (koreksi):**

```text
Klaim: "20240223_exam_schema_reset.sql berjalan SETELAH 22 seed dan menghapusnya"
Bukti saya — urutan CLI (perbandingan string JS pada digit sebelum '_'):
  exam_schema_reset.sql : posisi 22
  seed terakhir         : posisi 92
  → reset berjalan SEBELUM seed. AMAN, bukan berbahaya.

Klaim: "202402280003/0004 menyentuh voucher_claims sebelum dibuat"
Bukti saya:
  add_voucher_system.sql     : posisi 47   (membuat tabel)
  index_foreign_keys.sql     : posisi 50   (memakainya)
  → dibuat SEBELUM dipakai. AMAN, bukan berbahaya.
```

Sebaliknya, **urutan naif `ls`/glob-lah yang berbahaya**: di sana `exam_schema_reset.sql` berada di posisi 44 sementara seed pertama di posisi 5 — yaitu reset berjalan setelah seed. Ini kebalikan dari urutan CLI.

**Kesimpulan yang dapat dipertanggungjawabkan, dan cukup untuk mengubah rencana:**
Campuran timestamp 8/12/14 digit memang menciptakan **ambiguitas urutan**, dan `supabase/migrations/README.md` menyebutkan 16 dari 23 rujukan `.sql` secara salah karena menghilangkan komponen waktu 12 digit — persis kekeliruan yang menyembunyikan jebakan urutan ini. Tetapi **jangan mengutip klaim penghapusan data sebagai alasan**; alasan yang benar adalah folder ini **memang tidak dapat direplay** karena (a) tabel inti tidak pernah dibuat di dalamnya (G1/C1) dan (b) seed-nya tidak idempoten.

**Tindakan yang tetap benar:** perlakukan folder `supabase/migrations/` sebagai **arsip historis tambahan**, bukan sumber kebenaran skema. Jangan mencoba `db reset` atau membangun ulang environment darinya. Ini memperkuat C1, bukan menggantikannya.

**Catatan metodologi:** audit DB melaporkan bahwa service-role key di `.env.local` diterima untuk introspeksi PostgREST tetapi mengembalikan `42501` pada pembacaan data tabel. Pengalaman saya berbeda — probe saya berhasil membaca `products`, `leaderboards`, `entitlements`, `exam_attempts`, `exam_types`, dan `audit_logs` dengan key yang sama. Perbedaan ini tidak mengubah kesimpulan apa pun (keduanya sepakat tabel inti ada dan ACL `anon` tertutup), tetapi artinya klaim constraint/index/trigger yang bersumber **hanya dari bootstrap DDL** tetap berstatus `NEEDS VERIFICATION` sampai query katalog dijalankan.
